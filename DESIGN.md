# DSH Multi-Session Parallel Coding Scheduler Plugin — Complete Design Document v2.2

- Plugin package name: `dsh-swarm-scheduler-beta` (v0.2.7; the loader entry id stays `swarm-scheduler`, see §12.2.9)
- Target runtime: DeepSeek Harness `0.2.0-rc.2` (Cordis ~4.0.4)
- Purpose: the complete requirements specification for the plugin skeleton generated by `dsh-plugin-factory`
- Conclusion first: **90% of this design needs no new invention**. The DSH kernel already ships `ctx.agentTeams` (shared task DAG + atomic claim + roster + session-log persistence) and `@deepseek-ai/dsh-experimental-tool-agent-team` (9 ready-made tools), plus an `agent/status` (`idle ⇄ running`) event that enables **event-driven** scheduling. This plugin = adding "pure-scheduler Lead discipline + two-level decomposition + ready-pool view + Web panel" on top of that kernel layer.
- **New in v2.2**: §0.1 three hard loader constraints (measured; all fail silently); §0.2 spike conclusions and how `agent/status` is handled; §0.3 one correction to the v2.1 §14 tool surface. §1–§16 are unchanged from v2.1.

## 0.1 Hard Loader Constraints (measured; all three fail silently)

These three were hit one by one while mounting a `file:///` carrier in a real runtime — they are **not theoretical risks**: each one manifests as "no error, no log, looks normal".

| # | Fact | Failure symptom | Correct practice |
|---|---|---|---|
| 1 | **The loader does not await `apply()`** | An async `apply` (`export async function apply`) **never executes its body**, yet the entry still reports `fiberPhase: active` | `apply` must be **synchronous**. Hook all async work onto callbacks (`queueMicrotask` / events / `ctx.interval`); never await during activation |
| 2 | **Reading a service not declared in `inject` throws** | `cannot get property "agents" without inject`, thrown inside `apply` → plugin FAILED or silent with no output | `ctx` is an accessor object, so **every service you use must be listed in `inject`**. Declare `ctx.agents` too — do not assume it comes with the framework |
| 3 | **Module evaluation and `apply` are two independent failure domains** | When import resolution fails, `apply` never runs; if logging lives only inside `apply`, you get **total silence** (zero output, zero errors) | **Log one line at module scope too** — the only way to distinguish "never imported" from "imported but apply threw" |

**Constraint 1 is the most dangerous**: a dead plugin that never executes is indistinguishable in status bits from a healthy one — no signal at all. Treat this as non-negotiable when implementing.

**Debugging methodology**: first validate the mounting mechanism itself with a minimal plugin having **zero `@deepseek-ai/*` dependencies** (is `file:///` + `.ts` accepted?), then add real imports back step by step. The first mount takes effect in about 2 seconds.

**Platform limitation (not a design problem)**: an entry in `cordis.patch.yml` is **materialized only once, the first time the loader sees it**. Afterwards, changing `name`, changing `id`, or restarting the app never re-materializes it (4 measured attempts all failed while the host stayed healthy throughout). So **probes that need repeated iteration must not use patch mounting** — get them right in one shot.

## 0.2 spike conclusions

### spike-2 (does `agent/status` cover a teammate's idle transitions) — **could not be verified on a live system**

- The carrier was still not loaded after an app restart (`fiberPhase: null`), blocked by the §0.1 platform limitation.
- It also **cannot be self-verified by this agent**: `spawn_teammate` is unavailable in this tool classification, and §13 explicitly forbids using `ctx.subagents` to create workers — the party that triggers a teammate idle transition must be provided by the user or an independent runtime.
- Offline reconnaissance evidence: among the 10 session logs under `~/.dsh/sessions` there is **not a single `team/*` line**; the team feature has never been used, so there is no historical signal to read.

**Disposition: implement on the assumption that it is covered, but never depend on it.** The evidence is indirect but points one way:

1. The kernel agent-team itself subscribes to `agent/status` for team scheduling; if that event covered only the Lead, this library's own scheduler would not work.
2. The event catalog entry for `agent/status` does **not** carry the `@dshScopeScan unsupported` annotation, whereas `subagent/start` / `subagent/end` both do — the absence of that annotation implies distribution by agent scope is supported, i.e. a root ctx listener can see all agents.

**Zero-cost insurance** (which is why the unknown does not block implementation):

- `autoDispatchFallbackMs` fallback polling covers a missing event;
- every `pump()` round re-resolves the Lead (§6.3) without caching the reference;
- functionality is complete under either answer; only the latency changes from "immediate" to "≤ fallback interval".

### §8.3 Pitfall One — **confirmation must be filtered by yourself**

`session/event` carries no scope filtering, so a listener must filter by team session id on its own. **Defensive filtering must be written regardless**, independent of which way the signal points.

## 0.3 Correction to the v2.1 §14 tool surface

v2.1 §14 listed 6 tools, of which `team_panel_open` **cannot be implemented as a "tool"**: the panel lives in the browser while tools run on the host side, so **the agent cannot open the user's browser panel**. Implemented as a tool it could only return "please click the header button" — a fake capability.

**Correction**: leave the act of opening the panel entirely to the client half (the slot button in §9.1); the host side provides only a **read-only data route** (§5.3 option A). `team_panel_open` is removed from the tool surface.

|---|---|---|

## 0. Differences from the v1.0 Draft (read this section first)

The architectural intent of the v1.0 draft holds up completely, but several points conflict with the real runtime contract or reinvent the wheel. Every item below has source-level evidence.

| Claim in the v1.0 draft | Real runtime | How it is handled |
|---|---|---|
| Reuse `dsh-agent-teams`' shared scheduler and atomic claim | That capability **is already a DSH kernel service**, `ctx.agentTeams` (`@deepseek-ai/dsh-experimental-agent-team`), and ships built into the distribution | Bind the kernel service directly; do not reimplement |
| "Atomic claim guarantees two sub-sessions never take the same block" | The kernel `claim` uses **revision CAS**: a `revision` mismatch throws `TEAM_TASK_STALE_REVISION`; already held by someone else throws `TEAM_TASK_ALREADY_CLAIMED`; unmet dependencies throw `TEAM_TASK_BLOCKED` | Use it directly; the plugin owns re-read-and-retry on CAS conflict |
| Team state saved under `workspace/.agent-teams/`, with the Web panel reading the on-disk truth | The kernel `ctx.agentTeams` state is **persisted in the Lead's session log** (`team/task` events), projected by session projection, and replayable after a restart. The `.agent-teams/` directory is the file-persistence approach of the **third-party plugin `@nanmicoder/dsh-agent-teams`** and is **not** a kernel runtime path | Source of truth = session log (stronger than a file: same origin as the session and replayable); the plugin only mirrors "conclusions/outputs" to files |
| The three markers `big_task_id` / `small_task_id` / `assignment` | The kernel natively has only: `TeamTaskId` (e.g. `task-1`), `ownerName`, `subject` (≤200 chars), `description` (≤16384 chars), `writeScopes`, `blockedBy` | `small_task_id` = `TeamTaskId`; `assignment` = `ownerName`; `big_task_id` **has no native slot**, so it is carried by the `subject` prefix `[T1]` and validated by a plugin Config switch |
| "A sub-session automatically returns to idle after finishing its task, waiting to take the next block" | `list_agents`' `inactive` explicitly means "means no turn is executing, not a task is done"; `wait_agent` **never wakes inactive members** | The ready pool must be driven actively by the Lead or a plugin timer (see §3.5) |
| "The scheduler claims atomically based on true running/idle state" | `TeamMemberView.status` has 4 states: `running` / `inactive` / `provisioning` / `failed`. There is no `idle` | `inactive` + "no `in_progress` task in hand" jointly determine "dispatchable" |
| "An idle Agent always has a ready task block to take" | The Lead **cannot claim tasks itself** (by design intent), and a worker needs to be woken to claim one | The plugin's `swarm_dispatch` uses `reassign` (Lead-only) to dispatch and wake actively, see §3.6 |
| Memory-system branch isolation (§7 idea) | The DSH Cordis service catalog **has no memory service**; memory is outside this plugin's contract | §7 gives a workable approach: file handoff first, with memory marked as an optional soft option |
| "Refer to the branch operations and `send_message_by_branch` in dsh-session-fork" | No such API exists at runtime. Cross-session messaging has only `ctx.agentTeams.sendMessage(caller,{target})` (by **name**) and `ctx.subagents.sendMessage(sender,targetId,...)` (by **session id**) | Use `ctx.agentTeams.sendMessage`, taking the target from the roster name |
| "A/B/C are created as sub-sessions, initially idle" | Roster members must be created by `spawnTeammate`; **provider-owned subagent sub-sessions are explicitly excluded from the team** (`TeamRoster.tryMembership` returns `undefined` for sub-sessions carrying a subagent descriptor) | Workers must be created with `spawn_teammate`, **not** with `ctx.subagents.startContinuable` |

## 1. Core Architecture: Pure-Scheduler Lead + Equal Peer Sub-Agents

### 1.1 Role definitions (turned into executable constraints)

| Role | Runtime identity | Can do | Cannot do |
|---|---|---|---|
| Lead Agent | The live `Agent` of the current session (`exec.agent`), `membership.role === 'lead'` | Decompose, `team_task_create`, `team_task_list`, `wait_agent`, `spawn_teammate`, `send_message`, **`reassign`** | **Must not `claim` / `complete`** |
| Worker A/B/C | Continuable direct sub-sessions created by `spawnTeammate`, `role === 'teammate'`, name `^[a-z0-9]+(-[a-z0-9]+)*$` | `list` the ready pool, `claim`, `complete`, `send_message` to lead | Does not care about other workers; does not touch others' tasks |

### 1.2 How the hard constraint is enforced: a guard that keeps the Lead out of claiming

If the v1.0 rule "the Lead claims no task block" lived only in the prompt, a model could violate it. This plugin enforces it in two layers:

1. **Tool layer**: the plugin tool `swarm_task_claim` returns a rejection directly when `caller === lead` (no exception thrown; it returns a canonical value for `render` to explain).
2. **Guard layer**: `ctx.tools.guard(...)` or `tools/pre-execute` intercepts the kernel's own tool `team_task_update` and denies when `exec.agent` is the lead and `arguments.action` ∈ {`claim`}. This way, even a model that bypasses the plugin tool and calls the kernel tool directly cannot get a task.

> Why this works: the JSDoc of `ctx.tools.guard(guard)` states "one registered through `agent.ctx` applies only to that agent"; the `exec` of `tools/pre-execute` carries `exec.agent`; and returning a string from the guard denies the call.

### 1.3 Relationship to `dsh-session-fork` (revised)

Keep its **semantics**, replace its **mechanism**:

- Keep: the main session acts as secretary; sub-sessions hold independent context; only compressed results are reported back.
- Replace: `dsh-session-fork` schedules "branches", whereas this design schedules **small task blocks on a shared task board**, where workers are decoupled from tasks and whoever is free takes the next one.
- Note: the runtime has **no** `send_message_by_branch` / `branch` API available; cross-session communication uses the two message channels in the §0 table.

## 2. Two-Level Task Decomposition

### 2.1 Level one: big task blocks (big task / swimlane)

The Lead first splits the requirement into several "swimlanes". A swimlane is not a kernel object but a plugin-layer logical grouping, encoded into the `subject` prefix:

```
[T1] Data layer: schema and migrations
[T2] Service layer: REST endpoints
[T3] Frontend: list page
[T4] Integration: wire T1/T2/T3 together and pass end-to-end
```

Swimlane table (the plan the Lead gives in conversation, and also the `groups` input field of `swarm_plan`):

| Field | Constraint |
|---|---|
| `big_task_id` | `^[A-Za-z][A-Za-z0-9_-]{0,15}$`, validated by the plugin; rendered as the `[T1]` prefix |
| `title` | ≤ 60 chars (leaving room within the 200-char total for `subject`) |
| `goal` | The definition of done for that swimlane |
| `file_scope` | The directory prefix the swimlane is expected to touch, used for cross-swimlane conflict self-check |

### 2.2 Level two: small task blocks (the scheduling unit)

A small task block = one kernel `TeamTask` record. **The kernel assigns `task-N` as the unique identifier on creation** (`state.nextTaskNumber` monotonically increasing, `TeamTaskId`), which is naturally the `small_task_id` — no plugin-invented id space needed.

`swarm_plan` maps one small task block onto `createTask` arguments:

| Plugin field | Kernel field | Validation / limit |
|---|---|---|
| `small_task_id` (returned by the kernel) | `TeamTaskView.id` | Read-only, written back to the caller |
| `big_task_id` + `title` | `subject` = `[${big}] ${title}` | `requiredText(subject,200)`: non-empty after trimming and ≤200 |
| `brief` + `acceptance` + `inputs` + `outputs` | `description` | `requiredText(description,16384)` |
| `depends_on` | `blockedBy: TeamTaskId[]` | References must already exist and not be deleted, otherwise `TEAM_TASK_NOT_FOUND`; self-reference/cycle `TEAM_TASK_DEPENDENCY_CYCLE` |
| `write_scopes` | `writeScopes: string[]` | Each value is normalized by `writeScope()`: convert to `/`, strip the `./` prefix, strip a trailing `/`; **forbidden**: absolute paths, `C:` drive letters, empty segments, `.`, `..`, otherwise `TEAM_INVALID_WRITE_SCOPE` |

### 2.3 Hard constraints (the v1.0 four, turned into runtime semantics)

1. **Never forcibly split a logically indivisible block** — if it cannot be split into independent units, give the whole block to one worker. The kernel does not validate this; the §2.4 self-check list does.
2. **Minimum granularity**: one function / one file / one independent config entry / one independently verifiable behavior.
3. **Self-check before entering the pool**:
   - `A fresh teammate could do this from the description alone?` (does the description carry its own inputs/outputs/acceptance?)
   - `Would this block need another block's intermediate artifact?` (yes → add `blockedBy`, and do **not** put them in the same wave)
   - `Does any other ready block share a write scope?` (yes → serialize: add `blockedBy`, or merge into one block)
4. **Non-interference is not judged by "never conflicts" but by "conflicts are explicitly declared + conflicts are observable at runtime"**:
   - The kernel computes `writeScopeWarnings` in `projectTaskView`: when two tasks are **simultaneously `in_progress`** with overlapping scopes (`scopesOverlap`: equal, or one is a path prefix of the other), each side gains an extra `write scopes overlap with task-N`.
   - The semantics are explicit: **advisory, not a lock** (the JSDoc of `writeScope()` says: "without treating it as a lock"). So this plugin treats it as an **alert channel**, not a mutex. Real mutual exclusion comes from `blockedBy` serialization in §2.4.
   - If `swarm_dispatch` finds a non-empty `writeScopeWarnings` on the target block before dispatching, it must surface the warning in its result so the Lead can decide whether to serialize or merge.

### 2.4 Decomposition discipline (prompt clauses for the Lead)

- Within a single wave (simultaneously `in_progress`), **no file-level overlap**. Shared files (`package.json`, lockfiles, `index.ts` export barrels, route registries, global config) **do not participate in parallelism**; they must be owned exclusively by a dedicated "integration" small task block, with `blockedBy` on every block that produces them.
- Expected workload per block: a fresh sub-session can finish it within **one context window**. If it takes more, split another level down (`[T2.1]` sub-prefix) rather than letting one worker squat on a slot for a long time (this is exactly the root of the v1.0 §9 problem "A is still working on a big block").
- Prefer dependency-chain depth over width: `blockedBy` should express only **real** dependencies; do not serialize everything "to be safe" — that drives parallelism down to 1.
- Kernel limits (defaults, overridable by deployment config): `maxTasks = 256` (non-deleted task count), `maxMembers = 16`. Exceeding them throws `TEAM_TASK_LIMIT` / `TEAM_MEMBER_LIMIT`. So decomposition must be budgeted: ≤ 60 small blocks and ≤ 8 workers are recommended.

## 3. Scheduling Mechanism: Ready Pool + Atomic Claim

### 3.1 The precise definition of the ready pool

Kernel `TeamTaskView.ready` = `task.status === 'pending' && task.blockedBy.every(id => that task.status === 'completed')`.

So the **"ready pool"** = the set within `listTasks()` where `status === 'pending' && ready === true`. It automatically satisfies the two conditions of v1.0 §3.1:
- All prerequisite dependencies are completed (the definition of `ready`)
- It has not been claimed by any Agent (`pending` means `ownerId === undefined`)

> Note that `ready` already implies `status === 'pending'`; a block that is `in_progress` has `ready === false`. The plugin must not recompute this itself.

### 3.2 Atomic claim (guaranteed by the kernel; the plugin does not rebuild it)

`updateTask(caller, { taskId, expectedRevision, action: 'claim' })` performs CAS inside a single `journal.transact` transaction:

```
if (current.revision !== request.expectedRevision) throw TEAM_TASK_STALE_REVISION
if (current.ownerId !== undefined && current.ownerId !== caller.id) throw TEAM_TASK_ALREADY_CLAIMED
if (current.status !== 'pending' || !taskReady(state, current)) throw TEAM_TASK_BLOCKED
next = { ...current, status: 'in_progress', ownerId: caller.id }
```

Those three error codes are the proof that "two sub-sessions never take the same block": A commits first → revision +1 → B's `expectedRevision` goes stale → B gets `TEAM_TASK_STALE_REVISION`.

**The plugin's only responsibility** is one thing: an **honest retry protocol for CAS conflicts**.

```
claim(task_id):
  1. get(task_id) → { revision, ready, ownerName, status }
  2. if ready !== true            → return blocked (with blockedBy detail); do not retry
  3. if ownerName exists and ≠ self → return already_claimed
  4. update(task_id, revision, 'claim')
  5. catch TEAM_TASK_STALE_REVISION → re-read once, go back to 1; retry only once
  6. still failing → return conflict (the caller must re-decide; never spin forever)
```

### 3.3 The complete dynamic flow

```
Lead receives a coding requirement
  └─ swarm_plan(groups, small_tasks)            # one call creates the whole pool (partial failures can be resumed)
       └─ kernel: TaskBoard.create × N → task-1..task-N (blockedBy builds the DAG)

Scheduling round (triggered by the Lead or by the AutoDispatch timer)
  ├─ swarm_pool_status()                        # ready blocks + in-flight blocks + roster
  ├─ no ready block and no in_progress → pool empty: move to summary/acceptance
  ├─ ready blocks exist and a worker is free → swarm_dispatch(task_id, worker)
  │     ├─ update(action:'reassign', owner: workerName)   # Lead-only, pending→in_progress
  │     └─ sendMessage(target: workerName, work order)     # wake (inactive→running)
  ├─ ready blocks exist but no free worker and members < maxWorkers → spawn_teammate(work order)
  └─ ready blocks exist but no free worker and members at the limit → wait (wait_agent / next round)

Worker execution
  ├─ swarm_task_claim(task_id)                  # self-claim path; on CAS failure re-read and pick again
  ├─ write files (real output lands in the workspace)
  ├─ write the handoff note .dsh-swarm/reports/<small_task_id>.md (full evidence, see §4.3)
  └─ swarm_task_complete(task_id, expected_revision, summary, evidence, verify, confidence)
        ├─ sendMessage(target:'lead', compressed report)  # report first, so info is not lost if complete fails
        └─ update(action:'complete')

Lead summary
  └─ all ready=false and no in_progress → aggregate compressed reports by big_task_id per §4.2 → deliver + archive (§5.4)
```

### 3.4 Differences from Agent Teams (keeping the v1.0 intent)

The authorization model of the kernel's `team_task_update` is `lead || owner`: **the Lead may modify any task, a worker only its own**. The v1.0 requirement "the Lead claims no task" is **permitted** by that model (the Lead is not required to claim), so this plugin only needs to **prohibit it actively** rather than fight the kernel. The prohibition point is in §1.2.

### 3.5 Why active driving is mandatory (a major gap in the v1.0 draft)

The kernel states two things clearly:

1. `list_agents`: `inactive` **"means no turn is executing, not a task is done"** — a status bit cannot serve as a completion signal.
2. `wait_agent`: **"This never wakes inactive members"**, and its timeout range is hard-coded to `10000 ≤ timeoutMs ≤ 3600000` (default 30000). Out of range gives `TEAM_INVALID_ARGUMENT`.

Conclusion: **the pool does not flow by itself**; someone must run scheduling rounds. And in this runtime, a scheduling round **needs no polling** — three ready-made events can drive it.

#### 3.5.1 Event-driven dispatch (the core mechanism of this design)

| Event | Mode | Signature highlights | How this plugin uses it |
|---|---|---|---|
| `agent/status` | emit, agent scope | `{ agent: Agent; status: 'idle' \| 'running' }`, described as "`idle` ⇄ `running`… `idle` means no driver remains scheduled or active" | **Primary trigger**: any worker entering `idle` → run one dispatch round immediately (find a ready block + find an idle worker → hand out work) |
| `agent/error` | emit, agent scope | `{ agent, turn, step, error }` | Worker error → mark that task as "suspected failure"; the panel shows the abnormal state (the running/done/abnormal triad of v1.0 §5.1) |
| `agent/disposed` | emit, agent scope | `{ agent }` | A member disappears → reclaim the `in_progress` tasks under its name (`release` them back to the pool, or report `STALE_ASSIGNMENT`) |
| `tools/result` | emit, filtered by `exec.agent` scope | `exec` + `result` | Observe whether a worker's `swarm_task_complete` succeeded, for the panel and for auditing |
| `workspace/session-activity` | waterfall | Asks "what is still running in this session" before archiving | Safety check before batch archiving (§5.2 ④) |

**Key correction**: the kernel agent-team **emits no `team/*` events at all** (the event catalog contains no `team/task`, `team/change` or anything of the sort). The return value of `ctx.agentTeams.waitForChange()` is only `{ timedOut: boolean }` — **it does not tell you what changed** — and its minimum interval is 10 seconds. Therefore:

- **Do not** use `waitForChange` as the dispatch clock (10s granularity + no information).
- **Do** use `agent/status` for immediate triggering, and `listTasks()` to read the real state (reads are cheap, unprivileged synchronous calls).
- Add one more **low-frequency fallback timer** (`autoDispatchFallbackMs`, default 60s) to cover lost events, restarts, and "pool changes not caused by an agent".

```
worker finishes the current block → goes idle → fires agent/status(idle)
   → dispatch round:
       list    = team_task_list()                    # ready + in flight + done
       pool    = list.filter(t => t.ready)
       members = listMembers(lead)
       idle    = members.filter(role==='teammate' && status==='inactive' && nothing in_progress under its name)
       while (pool.length && idle.length) dispatch(pool.shift(), idle.shift())
       if (pool.length && memberCount < maxWorkers) spawn_teammate(next block)
   the fallback timer runs the same round every 60s (idempotent)
```

**Comparison of driving modes**

| Mode | Trigger | Latency | Cost |
|---|---|---|---|
| **A. Lead-driven** (available by default) | Lead calls `swarm_pool_status` and then decides | depends on the Lead's turn | zero resident cost; the Lead must stay active |
| **B. Event-driven AutoDispatch** (recommended) | `agent/status(idle)` | near-instant | requires holding the Lead's live `Agent` as caller (see below) |
| ~~C. Polling timer~~ | `setInterval` | ≤ interval | wasteful; fallback only |

**Implementation constraints for B (stated honestly)**: the plugin is a host-side Cordis plugin and can reach `ctx.agentTeams`, but the first argument of `listTasks/getTask/updateTask` is `caller: Agent`, which requires **a live Agent as the authorization credential** — the plugin itself is not an Agent. The feasible path:

- When `swarm_plan` / `swarm_pool_status` is called by the Lead, record that Lead's live `exec.agent` in plugin state (`Map<SessionId, Agent>`), and use it as the caller from event callbacks and timers;
- Each round, re-verify identity with `ctx.agents.get(id) === agent` (the kernel's `tryMembership` uses exactly this identity check);
- In the `agent/disposed` event, if the agent is that Lead, immediately unregister its dispatcher (which also stops the fallback timer along the way).

This path uses only documented APIs, but it is **the only part of this design that needs to be validated first**, and is listed as the first implementation step, spike-1 (§11). Even if validation fails, fallback A is fully functional (it is simply not automatic).


### 3.6 Why handing out work uses `reassign` instead of letting workers grab it themselves

- Letting 3 workers `list` at the same time and then `claim` on their own makes them collide on CAS (correct but wasteful, and every round has losers).
- `swarm_dispatch` performs a single-point `reassign` from the Lead side to a named member, which is **deterministic assignment**: one transaction moves `pending→in_progress` and hard-codes `ownerName`, with no contention.
- **Failure mode and repair**: `reassign` succeeds but the wake-up `sendMessage` fails → you get "assigned but the worker never ran". Repair: `swarm_pool_status` prints the `ownerName` of every `in_progress` task plus that member's `status`; if the member matching `ownerName` is `inactive` and has no running turn for longer than `staleAssignmentSec` (Config, default 180s), mark it `STALE_ASSIGNMENT`, and `swarm_dispatch` performs one re-send wake-up for that task (idempotent).
- The worker self-claim path is still kept (`swarm_task_claim`): it is for when the Lead only builds the pool without assigning each block, or for self-rescue after an assignment failure.

## 4. Context isolation and result reporting

### 4.1 Isolation model (assembled from runtime primitives)

| Isolation dimension | Mechanism | Basis |
|---|---|---|
| Context snapshot | `spawn_teammate context: 'fresh'` (default): a new member does **not inherit** the Lead's completed turns; only `'fork'` inherits | kernel tool description |
| Tool-surface narrowing | `spawn_teammate`'s `persona` / member tool set: a worker needs only `swarm_*` + file/command tools | `SubagentStartRequest.toolFilter` |
| Prompt narrowing | only the "worker protocol" is injected into the worker branch; only the Lead receives the "dispatch protocol" | the scoping scheme of §6.3 |
| Reporting narrowing | a worker returns only a compressed result; the full process stays in **its own session log** | inherent to the kernel: each member is a separate session |
| Source of truth | pool state lives in the Lead's session log (`team/task` events) and does not disappear with a worker | §6.4 |

**Note**: `SubagentRun`/`toolFilter` belong to the provider path of `ctx.subagents`; a worker must go through `ctx.agentTeams.spawnTeammate` (last row of the §0 table). So tool-surface narrowing must be implemented by **narrowing after the member is created** (registering `ctx.tools.restrict` on the worker's `agent.ctx` scope). This is listed as §11 spike-2.

### 4.2 Compressed reporting contract (the executable version of v1.0 §4.2)

`swarm_task_complete` requires the following fields and imposes hard caps on text length (Config `maxSummaryChars`, default 1500):

```jsonc
{
  "task_id": "task-7",              // required, = small_task_id
  "expected_revision": 3,           // required, CAS precondition
  "status": "done",                 // done | partial | blocked | failed
  "summary": "output summary of ≤1500 characters",
  "files": ["src/api/routes.ts"],   // paths of produced/modified files
  "evidence": "verification evidence: command + key output excerpt (the exact command must be given)",
  "verify_command": "pnpm vitest run src/api",   // reproducible acceptance command
  "confidence": "high",             // high | medium | low
  "report_path": ".dsh-swarm/reports/task-7.md"  // full handoff report
}
```

Semantic routing when `status !== 'done'`:

| status | Effect on the task board | Effect on the Lead |
|---|---|---|
| `done` | `update(action:'complete')` | enters the summary normally |
| `partial` | `complete` + the summary flags the unfinished part | the Lead creates a "continuation" small block and sets `blockedBy` on the original block |
| `blocked` | **does not complete**; `sendMessage(lead)` explains what is missing | the Lead decides to change dependencies / change the description / swap the worker (`reassign`) |
| `failed` | `reopen` (if already completed) or `release` (if in_progress) | the Lead changes the decomposition or falls back to manual work |

> Kernel action mapping: `claim` / `release` / `edit` / `set_dependencies` / `complete` / `reopen` / `reassign` / `delete`. Authorization: `edit`/`complete`/`release` and the like by the owner or the Lead; **`reassign` is Lead-only**; `delete` reports `TEAM_TASK_HAS_DEPENDENTS` while the task still blocks others, so it must be `reopen`ed / have its dependencies changed first.

### 4.3 File handoff report (the realization of v1.0 §7.4, and a key reinforcement of this design)

A compressed report loses detail, and detail must not live only in session logs. **A file must be written after every small task block completes**:

```
<workspace>/.dsh-swarm/reports/<small_task_id>.md
```

The front-matter states the markers, and the body carries the full evidence:

```markdown
---
small_task_id: task-7
big_task_id: T2
assignment: worker-api-1
status: done
verify_command: pnpm vitest run src/api
---
## Changes
- src/api/routes.ts: added the GET /items route
## Decisions
- pagination takes cursor rather than offset (reason…)
## Acceptance evidence
$ pnpm vitest run src/api → 12 passed
## Open items
- error-code mapping pending alignment with the T3 frontend
```

This design solves three things at once: cross-wave context transfer (the next block's worker reads the file directly instead of relying on the Lead to relay it), a backstop for memory leakage (the information lives in the file, not in memory), and later human review (the panel can locate it directly).

**Write path and sandbox discipline** (otherwise this design fails silently under restricted deployments):

- Writes must go through `ctx.fs` (`writeText` / `editText`), not `node:fs` directly — the compositional filesystem hangs the sandbox policy, the observation policy and the "read before write" policy on this layer; bypassing it bypasses every policy.
- The target directory is a **workspace-relative path** (default `.dsh-swarm/reports`), resolved against the Lead session's `cwd` (`SessionHeader.cwd`).
- The current deployment's file policy is `workspace-write` (only the session workspace can be written), so **nothing outside the workspace is ever written**; if the deployment changes to a read-only policy, writing to disk will fail — in that case `swarm_task_complete` must **degrade to "report as usual without persisting the file"** and leave `report_path` empty; never drop the task conclusion just because the handoff report cannot be written.
- `.dsh-swarm/` should be added to the workspace `.gitignore` (it is a one-off handoff record, not source code).

### 5.3 Panel data channel (the part that must be built new)

Problem: the truth about the ready pool lives on the **host** side (`ctx.agentTeams`, which needs live Agent credentials), while the panel lives on the **browser** side. There has to be a read channel.

**Option A (recommended, simple and controllable)**: the host half registers a **trust-check-protected** read-only HTTP route.

```ts
ctx.webServer.register({
  kind: 'exact',                       // 'exact' | 'prefix'
  path: '/api/swarm/board',            // must carry the plugin prefix: a duplicate (kind,path) throws
  handler: async (req, res) => {
    // Key: a custom web route does not go through Connection's trust check by default, so you must run it yourself
    const admitted = ctx.connection.admit({ headers: req.headers })
    if ('rejection' in admitted) {
      res.writeHead(admitted.rejection).end()
      return
    }
    res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify(view))
  },
})
```

Security points (otherwise this is an **unauthenticated information-disclosure surface**):

- The JSDoc of `ctx.webServer.register` only covers route occupancy, **not authorization** — it will not run Host/Origin checks or browser login validation for you.
- The correct approach is to call **`ctx.connection.admit({ headers })`**: its description is "Admit one request: it passes `requestRejection` and speaks for the operator, or it is refused with that status", returning `{ peer }` or `{ rejection: 401 | 403 }`. The description of `requestRejection` is exactly "Apply Connection's Host/Origin checks and browser authentication **to another Web route**" — it exists for this very scenario.
- A precedent of the same kind: `dsh-session-fork` explicitly declares **authority `loopback`** when building its own RPC channel. This plugin follows that discipline: **read-only, only this session's data, and it must pass admit**.
- If the deployment is reachable at a LAN-accessible address, a route that skips admit exposes the task board, file paths and member names to anyone on the same network segment — this goes into the implementation checklist and is not optional.

Remaining details:

- The signature of `WebRoute.handler` is **Node-native**: `(req: IncomingMessage, res: ServerResponse) => void | Promise<void>` (note that the `ServerResponse` name in the type table is taken by Cordis's RPC types; the actual implementation treats it as a Node res: `writeHead` / `end`).
- Registering the same `(kind, path)` twice **throws** ("route patterns are a composition-level contract"), so the path must carry the plugin prefix, and the path itself is configurable (`boardRoutePath`).
- The client reads it with a plain `fetch('/api/swarm/board?sessionId=…')` (same origin; the browser's session token is attached by the Connection layer) and refreshes by polling every 2s; no typert/@Remote generated schema is needed, avoiding out-of-tree build pitfalls.

**Option B (optional, if isomorphism with the kernel panel is wanted)**: copy the shape of `@deepseek-ai/dsh-experimental-client-ui-agent-team` — the host half registers a service decorated with `@Remote`, and the client half declares package names such as `@deepseek-ai/dsh-api-session-controller` in `dsh.client.inject` to obtain it. Cost: it needs typert-generated schema records, and a self-contained out-of-tree build is considerably more complex.

**Explicitly not done**: do not try to have the panel read `.dsh-swarm/` files directly without going through the host — the browser has no workspace filesystem; `workspaceFiles` is a host Remote service.

### 5.4 Differences from `dsh-subagent-workspace-ui` (per v1.0 §5.2)

## 6. Marker system

### 6.1 Where the three marker layers live

| Marker | Carrier | Searchability |
|---|---|---|
| `big_task_id` | `subject` prefix `[T1] ` | after a full `team_task_list`, the plugin groups by regex; the panel groups by prefix |
| `small_task_id` | kernel `TeamTaskId` (`task-N`) | native primary key, naturally unique, monotonic and CAS-able |
| `assignment` | kernel `ownerName` (`lead` or a member name) | native field, persisted with `team/task` events |

**Why `big_task_id` goes in `subject` rather than `description`**: panel search, human scanning, and `team_task_list`'s `subject` filtering are all more direct; the 200-character `subject` limit is also enough (the prefix is ≤ 18 characters).

**Optional strengthening**: with Config `strictGroupPrefix: true`, `swarm_plan` rejects any `subject` whose prefix does not match `^\[[A-Za-z][A-Za-z0-9_-]{0,15}\] `, turning a soft convention into a hard check.

### 6.2 Later inspection (the three questions of v1.0 §6.2)

| Need | Implementation |
|---|---|
| Completion status of all small blocks under one big task block | `team_task_list` → the plugin groups by `subject` prefix → `{ [T2]: { total, done, in_progress, pending, ownerNames[] } }` |
| Which sub-session completed a given small block | `TeamTaskView.ownerName` (+ the `assignment` in the `.dsh-swarm/reports/<id>.md` front-matter) |
| Which blocks in the pool are still unclaimed | `listTasks().filter(t => t.ready)` |

### 6.3 Prompt injection (the only global injection point; scoping must be handled)

`ctx.systemPrompt.section({ name, order, text, interpolate? })`:

- Registering on the **global ctx** → it enters **every** agent's system prompt, **including workers**. If you simply write "you are the dispatcher, maintain the ready pool", workers will try to act as team lead (recursive dispatch).
- Therefore: register **one** section, with `text` in **function** form, deciding the role from `context.scope` and returning the matching protocol:

```ts
export const SCHEDULER_ORDERS = { lead: 450, worker: 460 }   // exact values tuned per deployment

ctx.systemPrompt.section({
  name: 'swarm-scheduler-protocol',
  order: 450,
  text: (context) => {
    const agent = context.scope ? ctx.agents.get(context.scope as never) : undefined
    return agent && isLead(agent) ? LEAD_PROTOCOL : WORKER_PROTOCOL
  },
  // interpolate defaults; this section references no variables and stays plain text to reduce the assembly-failure surface
})
```

This must be verified: whether `AssembleContext.scope` can reliably resolve the current agent (the scope of `assemble({ scope })` is `ScopeKey = object`, so spike-3 must confirm its correspondence with `agent.ctx`). **Before that verification, the fallback** is to inject only LEAD_PROTOCOL and deliver WORKER_PROTOCOL verbatim through `spawn_teammate`'s initial prompt (each worker's assignment carries its own discipline clauses) — this fallback has zero risk, and **v1 is advised to take the fallback first**.

### 6.4 Persistence (correcting the path assumption of v1.0 §6.2)

- **Source of truth**: team tasks and members are events such as `team/task` in the Lead's session log, projected by the session projection, and are **already persistent + replayable**. After DSH restarts, `team_task_list` can still read the pool.
- **The `workspace/.agent-teams/` directory mentioned in v1.0 is not part of the kernel runtime** (that is file persistence built by the third-party plugin `@nanmicoder/dsh-agent-teams`). If a human-greppable mirror really is needed, this plugin may **additionally** write a `.dsh-swarm/board.json` snapshot, but it must be labelled "derived view, not the source of truth" and must never serve as the basis for dispatch decisions.
- The `workspaceChanges` service can provide a workspace-change summary/diff for each session — the panel's "output" column can use it directly instead of computing its own diff.

## 7. Memory isolation problem (an actionable plan)

### 7.1 Fact check

- The Cordis **service catalog of DSH contains no memory service** (no memory-type service exists in the full `Service.listService` catalog). Memory is not part of this plugin's contract surface.
- Therefore, the "attach `branchId` metadata to memory entries" of v1.0 §7.3 **cannot be implemented directly inside this plugin**: the plugin has no memory write channel, so it cannot inject metadata.

### 7.2 Primary plan: replace memory passing with the filesystem (v1.0 §7.4)

This is the plan this design adopts, already defined in §4.3:

1. Each small block produces one `.dsh-swarm/reports/<small_task_id>.md` (front-matter carries `big_task_id` / `assignment`).
2. The assignment **explicitly lists** the upstream handoff-report paths that the small block must read; the worker reads them itself, without the Lead relaying.
3. The worker's initial prompt hard-codes one sentence: **"Work only from the assignment and the handoff reports; do not rely on any cross-session memory."**
4. `context: 'fresh'` guarantees that the Lead's history is not inherited.

Benefit: even if memory gets crossed, the key information is still in the files (the exact wording of v1.0 §7.4), and it **does not depend on any unverified memory API**.

### 7.3 Optional strengthening (if a memory service exists later)

- **Branch-marker injection**: after `spawnTeammate`, write `big_task_id`/`small_task_id` into that worker's session metadata; if the memory service supports filtering by session, isolating by session is more thorough than tagging.
- **Self-check cross-validation**: before starting, the worker checks "does the information I cite come from this block's handoff report?"; the `evidence` field of `swarm_task_complete` requires file paths — if the evidence points only at "memory", the plugin emits an `UNSOURCED_EVIDENCE` hint at render time. This is a soft correction, in line with the positioning of v1.0 §7.3.
- **Hard correction** (rewriting memory-ownership markers) is not done: it exceeds authority and is irreversible.

## 9. Biggest advantage (conclusion retained)

It turns people looking for work into **work looking for people**.

- `dsh-session-fork` solves "a clean main branch and independent sub-branches".
- This design solves "maximum sub-branch utilisation": while the big block in A's hands is unfinished, B and C do not sit idle — the pool always holds ready, complete **small** blocks with declared dependencies and write scopes.
- The kernel provides atomic claiming (no duplicated work) + `blockedBy` (no idle waiting); this plugin adds **active assignment** (workers do not have to find work themselves) + **stale-assignment repair** (an assignment that never ran can still be detected).

| `swarm_report` | both | `sendMessage` | a pure message with no task change (asking for missing input, Lead broadcasts) |
| `swarm_stop` | Lead | `interrupt` + optional `delete` | stops all/specified workers; `delete` is blocked by `TEAM_TASK_HAS_DEPENDENTS`, so dependencies must be resolved first |

## 12. Acceptance criteria

1. Pool creation: after `swarm_plan`, `swarm_pool_status` can list every small block, with correct `ready` and `blockedBy` semantics.
2. Atomicity: two workers concurrently `swarm_task_claim` the same `task_id` — **exactly one** succeeds and the other gets `stale_revision` or `already_claimed`.
3. Discipline: a Lead call to `swarm_task_claim` is rejected; a Lead call straight to the kernel's `team_task_update{action:'claim'}` is denied by the guard.
4. Utilisation: `swarm_pool_status` reports at any moment both "the number of ready assignable blocks" and "the number of idle workers available to take work"; when ready blocks exist while workers are idle, `swarm_dispatch` completes assignment + wake-up within a single call.
5. Stale assignment: artificially create the state "`in_progress` but the worker has no turn"; `swarm_pool_status` must report `STALE_ASSIGNMENT`, and re-sending the wake-up via `swarm_dispatch` restores it.
6. Reporting: an over-long summary in `swarm_task_complete` is rejected; the `blocked` status does **not** mark the task complete; the handoff report file is persisted with complete front-matter.
7. Panel: an independent button appears in the header (the built-in `subagent-catalog` is not replaced); the panel shows the pool summary, swimlane grouping and members' tasks in hand; search filters by `task-N` / `[T1]` / member name; archiving archives without deleting sessions.
8. Restart: after DSH restarts, `team_task_list` can still read the pool and owners (session-log persistence).

## 12.1 Three architectural defects found by measurement (recorded after the v0.1.5 concurrency verification)

This section records three architectural defects confirmed during the **2026-10-16 multi-worker concurrency test** (3 teammates × 6 tasks × dual-pool mirroring). None of them is an implementation bug; each is a **conflict between interface semantics and orchestration assumptions**: the code executes as designed and the guards reject correctly, but the coordination layer lacks an explicit rule.

Evidence sources: the cross-pool split of `small-3-1` / `task-2`, the `not ready to claim` rejection of `task-2`, and the missing mirror for `small-4-3`.

---

### Defect one: `reassign` and `claim` are mutually exclusive

**Symptom**

After the Lead pre-assigned a task with `team_task_update{action:'reassign', owner:'worker-a'}`, requiring that worker to run `team_task_update{action:'claim'}` was rejected:

```
Error: team task "task-2" is not ready to claim
```

In the same test batch, changing the approach to "skip claim and go straight to complete" succeeded on the first try (revision 2 → 3).

**Root cause**

`reassign` **already completes the claim** semantically: it atomically sets the task to `status: 'in_progress'` with `ownerName` = the named member, so `ready` evaluates to `false`. But the precondition of `claim` is exactly `ready === true`. The two actions **contend for the same status bit** on the shared board, so they are inherently mutually exclusive — it is not a question of ordering.

Note the distinction between two kinds of rejection:

| Rejection text | Meaning | Is it a conflict? |
|---|---|---|
| `not ready to claim` | state-class rejection: the task is already owned (via reassign or someone else's claim) | no, an idempotent outcome |
| `stale team task ... revision N; current is M` | CAS-class rejection: the revision held by the caller has expired | yes |

**Impact**

- If an orchestration script writes both "assign via reassign" and "worker claims on its own", **the second step is bound to fail**;
- The failure is **deterministic** and does not depend on concurrency, so a single-task scenario hits it too (this run was a single-task pre-assignment);
- Because the error text does not point at the true cause, it is easily misread as a concurrency race, leading to wrongly added retry logic (retries are useless, because the state never rolls back).

**Recommendation (choose one, do not mix)**

- **A. Assign via `reassign`** (Lead-driven): after the Lead assigns, the worker `complete`s **directly**, skipping `claim`. Suits static allocation where "the Lead knows exactly who should do what".
- **B. Self-claim via `swarm_claim`** (worker-driven): the Lead only creates tasks without assigning, and workers grab from the ready pool themselves. Suits the dynamic load balancing of "work looking for people".

Mixing the two is the direct cause of the pitfall hit in this run. If a hybrid "pre-assign + self-claim" mode really is needed, then **use A for the shared board and B for the file pool** (since the two pools are independent — see defect two), and the orchestration script must explicitly state which pool takes which path.

---

### Defect two: no cross-pool mutual exclusion

**Symptom**

Two records of the same logical task were **half-taken by different workers**:

```
File pool small-3-1 : completed by worker-c     ← won by free pulling
Shared board task-2 : completed by worker-a     ← pre-assigned via reassign
```

`worker-c` clearly observed this split while pulling and voluntarily backed off ("the same piece of work was half-taken by different workers in the two stores; there is no cross-store mutual exclusion").

**Root cause**

The file pool and the shared board are **two completely independent stores and indexes**, differing in granularity and mechanism:

| | File pool | Shared board |
|---|---|---|
| Storage | `.dsh-tasks/<task_id>.json` | in-memory state of the `agentTeams` service |
| Mutual-exclusion primitive | `<task_id>.lock` (exclusive creation via `openSync('wx')`) | `revision` CAS |
| id space | custom (`small-3-1`) | kernel-generated (`task-2`) |
| Dependency expression | `blocked_by` (a file field) | `blockedBy` (a kernel field) |

`swarm_claim` locks a **file**, while `team_task_update` locks **shared-board state**; neither knows about the other, so **no cross-pool mutual exclusion or transaction exists**.

**Impact**

- The same task may be half-processed by two workers, **duplicating consumption** (in this run it caused no damage because the task was read-only and had no side effects);
- **Split attribution**: the two pools record different executors, so an audit cannot answer "who did it";
- **Dependencies cannot cross pools**: the file pool's `blocked_by` cannot constrain dispatch on the shared board;
- **Current mitigation**: the `invalid_state` guards of `swarm_claim` / `swarm_complete` (`is already completed`) catch **result overwrites** — in this run `worker-a`'s claim/complete on the already-completed `small-3-1` were both rejected, so **no second write occurred**. But the guard only prevents duplicate writes; it does **not** prevent duplicate execution.

**Recommendation: pick a single source of truth**

- **Shared board as authority**: the Lead mirrors, and workers use **only `team_task_*`**; the file pool serves merely as a Lead-side persistence snapshot (the `swarm_*` tools are not exposed to workers).
- **File pool as authority**: workers use **only `swarm_*`**; the shared board is used only for "work looking for people" dispatch and wake-up, and no trace on the shared board is required after completion.
- If dual writing really is needed, the Lead side must implement **single dispatch authority**: only the Lead writes the shared board, workers write only the file pool, and the Lead moves state between them — elevating cross-pool consistency from a "convention" to a "responsibility held exclusively by the orchestrator".

The lesson from this run: **with dual-pool mirroring and no mutual-exclusion mechanism, consistency depends on worker self-restraint**, and self-restraint does not hold when workers act independently.

---

### Defect three: blocked tasks cannot have a mirror pre-created

**Symptom**

`small-4-3` (`blocked_by: [small-4-2]`) was **skipped** during the Lead's mirror-creation phase; the shared board only ever held `task-1…task-6`, with **no mirror for it**:

```
worker-a's independent observation: "the shared board only has task-1…task-6, with no mirror task for small-4-3 (it should be task-7, but it does not exist)"
```

**Root cause**

The two readiness judgements are **two independent implementations**:

- File pool (this plugin): `ready ⇔ status === 'pending' && every entry in blocked_by is completed`
- Shared board (kernel): `ready ⇔ status === 'pending' && all blockedBy are complete`

The Lead's mirroring step takes the **file pool's `swarm_ready` output** as its input (mirroring only tasks that are "currently ready"), so **blocked tasks can never enter the mirroring flow** — until they become ready themselves, and by then the Lead is usually no longer inside a dispatch loop (in this run the Lead did not re-mirror between the two dispatch rounds).

**Impact**

- **Blocked tasks effectively fall outside the mirroring system**: `small-4-3` was eventually completed by `worker-b` in the file pool, with no corresponding record on the shared board, so **the cross-pool ledger stops balancing**;
- Combined with defect two the consequences amplify: when one side lacks a record, the other side's attribution cannot be cross-validated;
- The acceptance criterion "the two pools are eventually consistent" is **structurally unreachable** whenever dependency tasks exist.

**Recommendation (choose one of the two)**

- **A. Let the shared board carry dependencies too**: have `team_task_create` accept `blocked_by` and create the full mirror at creation time (including blocked tasks), with claimability governed by the kernel's `ready` judgement. Mirroring then becomes one-off and independent of blocking state. **First confirm the kernel's level of support** (whether it accepts cross-pool ids and whether mirror tasks must already exist).
- **B. Accept the delay of "mirror only when ready"**, but add a **remedial rule**: before every dispatch round the Lead re-runs `swarm_ready` and fills in ready tasks that are not yet mirrored; and **at wrap-up, treat the file pool as authoritative** when checking the shared board for omissions.

No remedy was applied in this run, so the gap persisted until wrap-up — hence this defect **remains an open item in the document**, not a fixed one.

---

### 12.1.1 The shared lesson of the three defects

All three point at the same structural fact: **this system has two independent state machines (file pool / shared board), and the coordinator (the Lead) has no single dispatch authority**.

- Defect one: two **actions** contend for the same status bit on the same state machine;
- Defect two: there is no mutual exclusion or transaction between the two **stores**;
- Defect three: two **readiness judgements** leave a blind spot in the mirroring flow itself.

Therefore, until a "single source of truth" is chosen, any dual-pool orchestration can rely only on the orchestrator's discipline, and discipline cannot be enforced by the system. **The next architectural decision point is exactly this: choose one, rather than patching further.**

## 12.2 Architectural decision: route B (file pool as authority)

**Decision date**: 2026-10-16 · **Applies to**: plugin ≥ v0.1.6 · **Basis**: the three measured defects in §12.1

### 12.2.1 Decision and rationale

**Chosen: route B — the file pool is the single source of truth for dispatch. The shared board degrades to an optional kanban view and takes no part in dispatch.**

There is only one reason, but it determines everything else: **the core goal is "work looking for people".** The file pool's trio forms exactly that chain:

| Stage | Tool | Semantics |
|---|---|---|
| Readiness judgement | `swarm_ready` | who may work |
| Atomic self-claim | `swarm_claim` | work actively lands in a worker's hands |
| Reporting | `swarm_complete` | the result returns to the pool |

The shared board's `reassign`, by contrast, is **the Lead assigning work**, the opposite direction — that is "people looking for work". The two are not two implementation paths for one goal, but **two different goals**. If the goal is "work looking for people", the assignment stage must not be triggered by the Lead.

**Rejected route A (shared board as authority)**: its dispatch is driven by the Lead's `reassign`, with workers accepting passively. That route could make the shared board the source of truth, but it turns "work looking for people" back into "people looking for work", conflicting with the project goal.

**Why this decision dissolves the defects rather than bypassing them**:

- **Defect one (reassign and claim contending for a slot) disappears**: under route B the Lead **no longer calls `reassign`**, so two actions never contend for the same status bit. Claiming simply does not happen on the shared board.
- **Defect two (no cross-pool mutual exclusion) disappears**: mutual exclusion can only arise for a resource **dispatched from two places at once**. Under route B the shared board **takes no part in dispatch** (it accepts no claim and performs no assignment), so the same task cannot be half-taken by two pools.
- **Defect three (blocked tasks cannot have a mirror pre-created) disappears**: dependency judgement is handled entirely by the file pool's `blocked_by`, and **mirroring no longer carries readiness semantics**. Whether a mirror includes blocked tasks becomes a purely display question (see §12.2.4).

**Key precondition (it must hold, or this decision is void)**: the five `swarm_*` tools are **visible and writable** to workers. This was confirmed by measurement on 2026-10-16: the teammate tool surface includes `swarm_plan` / `swarm_ready` / `swarm_claim` / `swarm_complete` / `swarm_status`, and all six tasks `small-3-1`, `small-3-2`, `small-3-3`, `small-4-1`, `small-4-2`, `small-4-3` were successfully claimed + completed by workers themselves.

### 12.2.2 The Lead's responsibilities (only three things)

1. **Create the pool**: `swarm_plan` writes into the file pool — this is the authoritative task definition (including `blocked_by`, `write_scopes` and acceptance criteria).
2. **Wake workers**: send one `send_message` to each `inactive` worker (the message need only point at "go to `swarm_ready` and find work"). **This is the Lead's only driving mechanism.**
3. **(Optional) create kanban mirrors**: when a panel/visualisation is needed, use `team_task_create` to create shared-board entries for tasks that are **currently ready**.

**The Lead explicitly does not**:

- ❌ call `team_task_update{action:'reassign'}` to assign work (that is route A's action)
- ❌ call `swarm_claim` / `swarm_complete` (those are the worker's job; doing them on the worker's behalf would mask whether "work looking for people" really holds)
- ❌ tell a worker "you go do task-X" (the wake-up message gives the method only, never a specific task — who gets which task is the outcome of `swarm_claim`'s atomic race)

### 12.2.3 The worker's responsibilities (a four-step loop)

1. `swarm_ready` — check the currently ready tasks
2. `swarm_claim` — atomic self-claim (`<task_id>.lock` exclusive creation; if you lose the race, move on to the next one — `already_claimed` is a normal outcome, not an error)
3. Execute the task
4. `swarm_complete` — report the result summary

**Wake-up flow**: Lead `send_message` → worker wakes → runs `swarm_ready` itself → `swarm_claim` → executes → `swarm_complete`. Workers do **not** need to coordinate with each other or look at the shared board; all collaboration happens through the file pool's atomic operations.

### 12.2.4 Handling defect three: the mirroring policy

Under route B the shared board **carries no readiness semantics**, so the mirroring policy is a pure display question; take the simplest rule:

**Mirror only tasks that are "currently ready"; blocked tasks are not mirrored.**

- Basis: the panel exists to show "work in progress / work available to claim", while a blocked task is neither claimable nor progressing at that moment, so mirroring it has no informational value;
- Consequence: blocked tasks **cannot be seen** on the panel. This is a **known and accepted** display incompleteness, not a defect — because it no longer affects any dispatch decision.
- If a complete kanban is needed later, the correct approach is to let `team_task_create` support `blocked_by` and create the full mirror in one call, **but that is not a current requirement**.

### 12.2.5 Corresponding plugin-side changes (v0.1.6)

Route B requires the plugin to **not depend on the team board**, so `inject` narrows from `['tools','agentTeams','agents','fs']` to **`['tools','fs']`**:

- `agentTeams` / `agents` are **used zero times** in the code (verified across the whole file: they appear only in comments). Declaring a service that no code reads is exactly the residue of assumptions such as "workers will use `reassign`" — the dependency exists only in the declaration.
- The implementation logic of the five tools is **unchanged** (the core behaviour of `swarm_plan` / `swarm_ready` / `swarm_claim` / `swarm_complete` / `swarm_status` is identical to v0.1.5).
- The shared-board mirroring feature is **retained** (for panel display), but the plugin no longer owns it and it no longer takes part in dispatch.

### 12.2.6 Risks this decision does not cover

1. **Single-process degradation**: when `ctx.fs` is refused by the sandbox, task writes fall back to `node:fs` (every return is marked `degraded`). Cross-process mutual exclusion is still guaranteed by `.lock` files, but **the fallback path bypasses `ctx.fs`'s version observation**. The file pool is now the single source of truth, which amplifies this risk — if a multi-process deployment happens later, it must be re-evaluated.
2. **Observability without panel-driven events**: the Lead can watch progress only through `swarm_status`; there is no event push. With a large number of tasks, the Lead must poll actively.
3. **Unverified**: the worker's `swarm_plan` permission. Measurement confirms that workers have the tool, but whether workers *should* be forbidden from creating pools has **not been tested**. The current convention is "only the Lead creates pools", enforced by discipline rather than by a guard.
4. **Read-only snapshots go stale**: the file pool records the **task definition**, and if a task's `description` hard-codes an "expected value" (e.g. "this file should be 31033 bytes"), that expected value expires as artifacts are rebuilt — the task record itself never updates, so **the record no longer matches reality**.
   - **Measured this time**: the description of `small-3-1` required checking the byte count of `lib/index.js`; that artifact was rebuilt during the worker's check (31033 B / 4-key `inject` → 31009 B / `inject = ["tools","fs"]`), and the file-pool record promptly went stale.
   - **Recommendation**: make later task `description`s say "**report the measured value**" instead of "**verify that it equals some value**". The former is always true; the latter depends on a mutable external fact. When an assertion is needed, the source of the measured value should be written into the description as well (for example, "as of git commit or version X").
5. **`Get-Content` line counts are untrustworthy (an engineering caveat; see appendix A for details)**: if `Get-Content` is used to count the "lines" of a UTF-8 file during acceptance, the result is **systematically too small** — in this measurement the same file reported 786 against a true value of 1045. Any check involving line or character counts must use `-Encoding UTF8` or the LF byte count, otherwise the acceptance conclusion rests on a wrong number.

> The first two came from the concurrency verification (the measurements in §12.1); the latter two came from the route-B closed-loop verification. All four belong to **"the gap between the record and reality"** — different manifestations of one class of risk.

6. **Members cannot be removed once created**: among the 11 methods of `ctx.agentTeams` there is **no member-deletion path at all** — no `remove` / `dismiss` / `release` / `deleteMember` / `evict`. Once a member is created by `spawnTeammate` it enters the roster, and `interrupt` can only abort its current turn (its exact description: `Interrupt one live teammate turn without clearing its pending inbox`); the member itself remains. `TeamMemberView` has only 9 read-only fields (`id` / `name` / `role` / `status` / `description` / `provider` / `context` / `model` / `diagnostics`), of which `status` is a four-state observed value rather than a settable property, and **there is no `createdAt` or `parentSessionId`**.
   - **Impact**: the roster **only grows**. In this measurement the six members `worker-a` through `worker-f` stayed on the roster across several restarts, all `inactive` yet impossible to clear. The only cleanup path the service description offers is session-level: `agentTeams` is *"backed by the exact live Lead Session log"*, so members vanish wholesale when the **Lead session ends** (error code `TEAM_DISPOSED`).
   - **Countermeasure**: change protocol item 2 to **prefer reuse** — first `list_agents` to find `inactive` members and wake them with `send_message`, and only `spawn_teammate` when no member is idle. This controls the roster's growth rate but **cannot reclaim** already-created members.

7. **No reclamation after a task is claimed**: the five tools have no release / reopen / timeout reclamation. A task's `claimed` state **has no expiry mechanism**, so when the lock-holding worker disappears before finishing (interrupted, closed, crashed) the task is **stuck in `claimed` forever**, and **every downstream task whose `blocked_by` names it becomes permanently unreachable**.
   - **Measured this time**: after `small-6-1` was claimed by `worker-d`, that worker was closed before finishing; `small-6-1`'s `claimed_at` stayed at `2026-10-16T16:14:05Z` with an empty `result`, and **the whole pool's `small-6-3` could therefore never become ready**. The lock also **persists across sessions** (still there the next day) and does not disappear with any automatic cleanup.
   - **Impact**: this is a **single-point permanent block** — one vanished worker can freeze an entire dependency chain, and no tool can unlock it (file-pool tasks are hand-written JSON, and `team_task_update`'s `delete` only affects the shared board).
   - **Countermeasure**: **add a sixth tool, `swarm_release`** (v0.1.9). Behaviour: change `claimed` back to `pending` and clear `claimed_by` / `claimed_at`; a non-`claimed` state returns `invalid_state`, and a missing task returns `not_found`. **Only `claimed` may be released** — a completed task can never be "washed back" to todo by it.
   - **Follow-up: lightweight failure reclamation** (v0.2.5). `swarm_release` only helps if the Lead knows to call it, and nothing told the Lead that a claim had been held too long. `swarm_status` now **marks a claim as `STALE`** when it is older than `config.staleAssignmentSec` (default **600 seconds**), printing the age alongside it (`[STALE, claimed 15m ago]`) and adding a count to the summary line (`claimed 2 (1 stale)`). The response also carries `stale` and `stale_after_sec`.
     - **This makes a timeout visible; it does not act on one.** Nothing is released automatically — the Lead reads the mark and decides. The distinction is deliberate: **the plugin cannot tell "stuck" from "slow"**, so an automatic reaper would eventually steal work from a worker that was merely thinking hard, and the result would be two workers on one file. Marking is information; reclaiming is a judgement, and the judgement needs a context the pool does not have.
     - **The threshold is a reporting knob, not a reaper setting.** Set `staleAssignmentSec: 0` (or a non-finite value) and staleness is simply never judged — the plugin clamps it to "do not judge" rather than treating a bad value as "everything is stale". A claim whose `claimed_at` cannot be parsed is also never called stale: the age is unknown, and guessing it would produce a false alarm.
     - **Automatic reclamation would need a Watchdog** — something that can observe worker liveness directly (the kernel's `agent/status` exists for this) rather than inferring it from a timestamp. **Not implemented**, and not claimed to be.
     - **`staleAssignmentSec` is a field that came back.** It was one of the twelve dead configuration fields removed in v0.2.4, and it returns in v0.2.5 for a real purpose: it is read by the same change that declares it, which is the rule §12.2.7 wrote down after the dead-config feedback.
   - **Follow-up: admission control and lock cleanup** (v0.2.6). Two gaps remained after `swarm_release` and staleness marking, both found by walking the claim path rather than by a fresh failure:
     - **`write_scopes` was still advisory, so it did not prevent the thing it warned about.** `swarm_claim` now reads every claimed task and **refuses a claim whose scopes overlap one of theirs**, returning `scope_conflict` with the conflicting task id and the overlapping scope pair. A correction is recorded alongside it, because the earlier phrasing invited the wrong reading: **this pool never emitted an overlap warning of its own.** The soft, early view is `swarm_ready`'s `scope:` listing — the declared scopes, so a planner can see a collision coming — and the hard view is the refusal at the moment of admission. `writeScopeWarnings` is the *kernel*'s rule for the team board (Appendix B), not a function of these seven tools; "advisory" described the posture, never a message this plugin printed.
       - **Granularity is directory-level, deliberately.** `src` and `src/api` overlap, so two tasks that would edit *different* files under `src` are still refused. The trade is explicit: a false refusal costs one serialisation step, a false admission costs a silently overwritten file. Narrower scopes are the escape hatch.
       - Normalization mirrors the kernel's own `writeScope()` (forward slashes, no `./`, no trailing slash) because these values are compared with each other, and `src/api` versus `./src/api/` is one scope written two ways.
     - **A claim has two halves, and only one was being reclaimed.** `swarm_release` changed the status but left the `.lock` behind, so a worker that died *inside* its lock window left a task that read `pending` yet answered `already_claimed` to every future claimer — no holder to blame, no way out. Now `swarm_release` deletes the lock too (`lock_removed` says whether one was there), and `swarm_claim` clears a **residual lock** found while the task reads `pending` (`stale_lock_cleared` says so). The rule that fell out: **state and lock are two halves of one claim; every path that ends a claim must close both.**
     - **A third defect surfaced only because the new tests ran.** `completeTask` accepted a `pending` task, so work nobody had claimed could be marked `completed` — reading as "someone did this" when nobody did. It now requires `claimed`, which is what keeps `claimed_by` meaningful. This is the strongest argument for the v0.2.6 test suite: the gap had been recorded as missing *coverage*, and it turned out to be a missing *guard*.

> Items 6 and 7 come from a dedicated review of "member and task lifecycle". They differ from the first five: the first five are about "the gap between record and reality", while these two are about **"a creation path exists but a reclamation path does not"** — a roster that only grows, and a task pool you can only claim from, never return to.

8. **The file pool could not edit dependencies, so same-file serialization could not be enforced** — *fixed in v0.2.1*: the pool exposed six tools (`swarm_plan` / `swarm_ready` / `swarm_claim` / `swarm_complete` / `swarm_status` / `swarm_release`) and **none of them could change `blocked_by` after creation**. A task's dependency set was fixed at `swarm_plan` time.
   - **Why this mattered**: the only way to keep two workers off the same file is a `blocked_by` chain, so that decision was locked in at planning time and **could not be repaired mid-flight**. Attempting the repair through the team board failed, because the two stores are independent (item 2): `team_task_update{action:'set_dependencies'}` against a file-pool task returns `team task "small-7-2" not found`.
   - **Measured consequence**: when `DESIGN.md` was split into three line ranges (`small-7-1` / `7-2` / `7-3`) **in parallel**, two workers each hit `FS_STALE_VERSION` (`file changed since it was read`), and one boundary overlapped — a worker translated line 259, which belonged to the neighbouring task. Both workers recovered correctly (re-read → rebase → retry, never overwriting the other's work), but **the collision was structural, not incidental**.
   - **Countermeasure — done (v0.2.1)**: **`swarm_set_deps` has been added**, the seventh tool. It replaces one task's `blocked_by` list and validates two things a dependency graph needs: every referenced id must exist (`invalid_dependency` — a dangling blocker would otherwise make the task permanently unready, since a missing task never counts as completed), and the new edges must not close a cycle (`cycle_detected`, detected by walking the graph downward from the proposed blockers and refusing if the walk reaches the task itself; a self-reference is just the shortest cycle and needs no special case).
   - **Still true**: split by **file**, not by line range, whenever more than one worker must run at once. `swarm_set_deps` makes a repair possible, not the original mistake advisable.
   - **`swarm_set_deps` is LEAD-ONLY, deliberately centralised**: a worker that hits a dependency conflict reports it to the Lead via `send_message`, and the **Lead** decides and edits. Workers must not call it themselves. The reason is not authority for its own sake: `blocked_by` is a shared graph, so concurrent edits by several workers would race each other and could interleave into exactly the cycle the validation exists to prevent. Serialising the decision on one writer is what makes the cycle check meaningful rather than merely best-effort. The tool description states this ("LEAD ONLY — do not call this as a worker"), and the protocol carries the same instruction as step 6.

9. **Read-only verification is not independent when the verifier is the author**: `small-7-4` (the DESIGN.md verification task) was claimed by the same worker that had already translated `small-7-2` and `small-7-3`. Its mechanical checks (CJK scan, fence count, line-count unit, identifier presence) remain valid, but its **semantic spot-check of its own translation proves nothing**.
   - **Why it happened**: the pool assigns work by atomic claim, and `swarm_ready` returned the verification task as ordinary ready work — nothing in the task model distinguishes "anyone may do this" from "someone other than the author must do this".
   - **Mitigation used here**: the Lead ran an independent third-party pass (byte-level CJK scan, structural comparison against a pre-translation excerpt, identifier-preservation check, code-block inspection) and reported it separately. A structural fix would be a task field naming an excluded owner, or a convention that verification tasks are assigned by the Lead only after the author has finished.

> Items 8 and 9 come from the DESIGN.md translation run itself. They complete the pattern: after "record vs reality" (1–5) and "creation without reclamation" (6–7), these two are about **"coordination gaps the task model cannot express"** — a planned dependency that cannot be amended, and a verification that cannot be made independent by the pool alone.

### 12.2.7 Post-release feedback (v0.2.4)

Seven issues were reported by users after the first public release. All seven were **documentation, configuration-surface or test-coverage defects — none affected runtime behaviour** — but each one could mislead a new user, so each is recorded with what was wrong and what changed.

1. **The source comment named the wrong bundle** (fixed). A comment in `src/index.ts` said `agentTeams` comes from `@deepseek-ai/dsh-experimental-agent-team`; the mountable bundle is **`@deepseek-ai/dsh-experimental-agent-team-profile`** — the difference matters because the non-`-profile` package has no `dsh.bundle.patch` at all and mounts nothing. The name was also split across a line break, which made the error invisible to a plain text search. **Impact**: a user following the comment would mount a package that registers nothing, and `agentTeams` would stay missing — precisely the failure §12.1 documents.
   - Note: the report said "4 occurrences"; measurement found **one** real mis-naming plus one prose mention of "the agent-team profile layer", which was already accurate. Recorded as a reminder that a reported count is a claim to verify, not a fact to act on.

2. **The bundle's rollback path was not documented** (fixed). README said removing the bundle line restores the native subagent tools, but did not say that **removing only the plugin leaves the swap in place** — the bundle is independent of the plugin. **Impact**: a user disabling the plugin would still be missing `subagent` / `list_agents` (native) and have no idea why.

3. **`write_scopes` was described as advisory but never as *unenforced*** (fixed). It produces a warning on overlap and nothing else: two tasks writing one file are **not** blocked from running in parallel and can still overwrite each other. **Impact**: a user could reasonably read "advisory" as "soft lock" and skip the serialisation that actually protects them. *(One precision, added with the v0.2.6 fix: "produces a warning" describes the kernel's `writeScopeWarnings` on the team board, not this pool — these seven tools printed no overlap warning at all. The impact was therefore the larger one: nothing warned and nothing refused. See §12.2.6 item 7.)*

4. **`tasksRoot` was documented only as a pitfall, not as required setup** (fixed). Its default is empty, and empty falls back to `process.cwd()` — the **profile directory** on DSH Desktop, not the session workspace. The README mentioned this under "pitfalls found the hard way" but the installation section never told anyone to set it. **Impact**: the pool would be created somewhere other than the workspace, which is the exact mistake this project made during development. The installation section now carries a mandatory `tasksRoot` step with a YAML example. **Second half fixed in v0.2.7**: documenting a requirement does not enforce it — the code still accepted the empty default and fell back quietly. `resolveTasksRoot` now throws at activation instead, so the requirement is a rule rather than advice. See §12.2.8.

5. **`config.ts` carried dead configuration** (fixed). Of 14 declared fields, only **two** were read anywhere in `src/`: `tasksRoot` and `debugLogPath`. The other **twelve** were vestigial from the pre-route-B design — `maxWorkers` / `maxSummaryChars` / `handoffDir` and friends belonged to `pump.ts`, `handoff.ts` and `board.ts`, all deleted during the file-driven rewrite. Anyone setting them changed nothing and got no error to explain why.
   - **Fixed in two steps**: `autoDispatch`, `workerProvider`, `boardRoutePath` (plus `pollIntervalMs`) went first, then the remaining eight (`maxWorkers`, `maxTasksPerPlan`, `autoDispatchFallbackMs`, `staleAssignmentSec`, `maxSummaryChars`, `strictGroupPrefix`, `handoffDir`, `maxHandoffBytes`).
   - **`Config` now declares exactly two fields.** `config.ts` shrank from 78 to ~40 lines. The interface carries a comment stating the rule that follows: **if a setting is added back, it must be read by code in the same change.**
   - A configuration surface that accepts values it ignores is the same class of defect as documentation that describes behaviour the code does not have. Both were present in this release.

6. **The dependency on an experimental package was understated** (fixed). The README said the bundle must be mounted, but did not spell out the consequences: the package is `experimental` by its own label, **not in any DSH default bundle**, may **change with a DSH update**, and this plugin does not guarantee long-term compatibility. If DSH promotes or removes it, the installation steps change. **Impact**: a user could mount it once, treat the setup as settled, and be broken by an unrelated DSH update. Now recorded as its own known limitation with all three consequences.

7. **No automated test suite** (recorded honestly, **partially fixed in v0.2.6**). Concurrency correctness was established by **manual measurement**, not by tests that re-run on every change: the single-task closed loop, a 3-worker concurrent run with atomic claiming, the route-B closed loop, all four `swarm_set_deps` return paths, and `swarm_release`. **Impact**: the behaviour was verified on the days it was tested, and **nothing re-verifies it after a change**. Recording this is deliberate — an absent test suite is a fact a user should be able to learn from the README rather than by discovering a regression.
   - **Fixed for the core logic**: `test/task-store.test.ts` runs on Node's built-in runner (`npm test`, **no new dependency**, Node 22.18+ or 22.6+ with `--experimental-strip-types`, since the suite runs the `.ts` sources directly) and covers 25 cases over `claim` / `release` / `complete` / `setDependencies`, the `write_scopes` admission check, residual-lock cleanup, readiness and staleness. The suite boots no host: it passes a minimal `Context` stub whose `get('fs')` returns `undefined`, which drives the store down its documented `node:fs` fallback — the same path a sandboxed deployment ends up on. Each test gets a fresh `os.tmpdir()` pool and removes it afterwards.
   - **Still manual**: *concurrent* behaviour. A single process cannot honestly unit-test cross-process lock contention, so the atomic-claim claim continues to rest on the 3-worker measurement described in §12.1. The tests protect the logic; they do not re-verify the concurrency.
   - **The suite needed a second script, because the first one did not run where it was written.** `node --test` spawns one child process per test file with piped stdio, and a sandboxed shell refuses that with `spawn EPERM` — measured here, and a property of the environment rather than of the assertions. `npm test` stays the conventional entry point; `npm run test:sandbox` adds `--test-isolation=none` and runs the same cases inside one process, which costs nothing for a single-file suite. Recorded rather than worked around silently: a test command that only runs outside the tool that wrote it is a defect in the command, not in the reader.
   - **The suite earned its place on its first run**: it failed, and the failure was a real defect — `completeTask` accepted a `pending` task, letting work nobody had claimed be marked `completed`. See the v0.2.6 follow-up in item 7 of §12.2.6.

> **The pattern across all seven**: the plugin's *behaviour* was verified extensively (§12.2.1–§12.2.6), but its *description* was not. Six of the seven defects are places where the documentation or the configuration surface asserted something the code did not do; the seventh is a capability that was simply never claimed. Release verification should therefore treat "does the documentation match the code, and does the configuration match what is read" as a first-class check — not a follow-up.
>
> Two of these were reported as counts that measurement disagreed with: "4 occurrences" of the bundle name was **one**, and "3 dead config fields" was **twelve**. A reported count is a claim to verify, not a fact to act on.
>
> A third pattern arrived with v0.2.6: **writing the tests found a defect the manual runs had missed.** The absence of tests was recorded here as a coverage gap; it turned out to be a correctness gap as well. That is the argument for the suite in one line.

### 12.2.8 Follow-up: `tasksRoot` fail-fast (v0.2.7)

Item 4 of §12.2.7 was fixed in v0.2.5 by **documenting** the setting. Documentation enforces nothing: the code still accepted the empty default and quietly resolved it against `process.cwd()`, which on DSH Desktop is the **profile directory** — so a deployment that skipped the step looked healthy while writing every task somewhere its user never opens. Same class as the rest of this section, one level deeper: the docs had been corrected, the **default** had not.

- **The change**: `resolveTasksRoot` in `src/config.ts` refuses an empty (or whitespace-only) value and throws a message that names the setting, the consequence, the path the fallback would have used, and the YAML line to add. `apply` calls it **before** constructing the store, so the throw lands in the existing `catch`, which records the reason and rethrows — the fiber reports `failed` rather than `active` with an unusable pool.
- **Why activation is the right place to refuse**: `registerFileTools` runs after the store is built, so a refused start registers **nothing**. A half-configured plugin that answers `not_found` to every call is worse than one that refuses to start, because the first failure mode is indistinguishable from "the pool is empty" — the user debugs the symptom, not the cause.
- **Trade-off, stated plainly**: a deployment with an empty `tasksRoot` now fails to load where it previously "worked". That is the intent, not a regression — its previous output was a pool in a directory nobody looks at. The remedy is one config line, and the error prints it.
- **Verified**: `test/config.test.ts` (5 cases) pins the refusal for `''` and whitespace, asserts the message actually explains the fallback and shows the line to add (a refusal with a useless message is just an obstacle), and pins that a configured absolute path is returned unchanged with surrounding whitespace trimmed. Handing the resolver the value from a real profile (`tasksRoot: 'C:/Users/…/default-workspace'`) returns it unchanged, so the change refuses omissions, not correct configurations.
- **Deliberately still open**: a **relative** `tasksRoot` is accepted and still resolves against `process.cwd()` — the same trap in a different disguise. Rejecting it was out of scope: it would break deployments that mount the plugin from the very workspace they schedule, and the reported defect was the empty default. Recorded here rather than fixed quietly.

### 12.2.9 Renamed to `dsh-swarm-scheduler-beta` (v0.2.7, code unchanged)

The package name, the loader row in `cordis.patch.yml`, the `PLUGIN_ID` that keys the client module registry, and the exported `name` of both halves now read `dsh-swarm-scheduler-beta`. The whole chain moved together, and not from tidiness:

- **`tsup.config.ts` states the constraint**: the web loader keys its module registry on the id, and that id must equal `package.json` `name`. It is injected as a `define`, so a mismatch is not a type error — the client half would simply register under a key nobody looks up.
- **The cordis patch resolves the inserted row by package name.** A stale value there is a boot failure, not a warning, which is the same silent-or-fatal asymmetry this page has recorded for every other loader constraint.
- **The profile side is part of the change**: dependency key, `file:` specifier, the `bundles` entry and the `node_modules` directory all carry the new name, because Node resolves a `file:` dependency by directory name. Renaming only the package would leave the old directory resolvable and the new name missing.

What deliberately did **not** change:

- **The loader entry id** stays `swarm-scheduler`, so an existing profile `cordis.patch.yml` override — including `tasksRoot` — keeps applying to the renamed package. Renaming the id would have orphaned every deployment's configuration.
- **The local repository directory** keeps its old name; nothing resolves it, and moving it would invalidate the `file:` paths in already-configured profiles.

Consequence for the repository itself: the GitHub repository was renamed to `dsh-swarm-scheduler-beta` to match, so `repository.url` in `package.json` points at the new name. GitHub redirects the old URL, which is why clones made before the rename keep working.

## Appendix A. Engineering caveat: the line-count unit for UTF-8 files

**Problem**: in this repository `DESIGN.md`, the plugin source and the task JSON are all **UTF-8 without BOM**, while Windows PowerShell's `Get-Content` **decodes with the system ANSI code page by default (GBK / CP936 on this machine)**. UTF-8 Chinese characters are multi-byte sequences; decoding them as GBK double bytes produces mojibake and, during decoding, **swallows part of the LF bytes**. Therefore:

```powershell
(Get-Content $f).Count              # ❌ 786   —— too small, and unstable
(Get-Content $f -Encoding UTF8).Count  # ✅ 1045
```

**Measured this time** (`DESIGN.md`, 74,921 bytes):

| Unit | Result | Verdict |
|---|---|---|
| `Get-Content` (default, GBK) | **786 lines** | ❌ wrong — DBCS decoding swallowed 259 LFs |
| `Get-Content -Encoding UTF8` | **1045 lines** | ✅ |
| LF byte count (`ReadAllBytes`, counting `0x0A`) | **1045** | ✅ baseline |
| `read` tool `total` | **1045** | ✅ |

**Consequence**: during this development, the line counts in several interim reports ("839 lines", "742 lines", etc.) were **inaccurate** because of this unit. The numbers themselves do not affect functionality, but they mislead acceptance judgement — for example, a check such as "was the file written completely?" can reach a wrong conclusion.

**Rule (to be followed from now on)**:

1. To count lines/characters of UTF-8 text you **must** add `-Encoding UTF8`, or switch to a byte-level method:

   ```powershell
   $lf = 0; foreach($b in [System.IO.File]::ReadAllBytes($f)){ if($b -eq 10){ $lf++ } }
   ```

2. Prefer the `read` / `grep` tools to read files — they handle UTF-8 and naturally avoid this problem.
3. When writing acceptance scripts, do **not** use bare `Get-Content` for any counting or string comparison; if content comparison is required, decode explicitly first.
4. The same applies to `Select-String` (same default encoding) and `Out-File` (which writes UTF-16LE by default; use `-Encoding utf8` explicitly).

> This caveat has nothing to do with dispatch, but it is a **hard constraint of the acceptance stage**: a wrong unit makes a correct implementation look like a failure, and vice versa.
